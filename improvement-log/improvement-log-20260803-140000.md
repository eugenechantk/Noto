## Log

### 2026-08-03 — Chained 5 UI actions without verifying

**What happened:** Ran tap→capture→tap→tap→capture in one bash call. The middle taps silently failed because the sheet presented a different accessibility hierarchy, so both captures recorded the same stale screen.
**Why this was wrong:** The flowdeck skill explicitly says "never chain more than 2-3 actions without verifying." I ignored it to save round trips and had to redo the work anyway.
**What better looks like:** Cap chains at 2 actions. When a sheet/menu/popover is involved, dump the accessibility tree before targeting anything inside it — presented surfaces re-parent their elements.

### 2026-08-03 — Readwise sync polluted the test vault

**What happened:** A freshly created, freshly erased simulator kept filling the seeded vault with 300-600 real Reader articles. I assumed a stale keychain and erased the device twice before finding the cause.
**Why this was wrong:** I treated "fresh simulator" as proof of "no credentials" and chased container-UUID red herrings instead of reading the code path that writes those files. Reading `ReadwiseSyncController.activeToken` → `loadOrSeedToken()` → `bundledTokenProvider` would have answered it in one step.
**Root cause:** `ReadwiseDefaultToken.txt` ships inside the app bundle and re-seeds the keychain on every launch, so erasing the device never helps.
**What better looks like:** When app state reappears after an erase, read the seeding code path first — the source of truth is the code, not the device. Persisted state that survives a wipe is almost always baked into the build.

### 2026-08-03 — flowdeck guard hook blocks shell variables

**What happened:** `-S "$NOTO_UDID"` was blocked by the isolation hook even though the variable held the correct session UDID.
**Why this matters:** The hook inspects the raw command string before the shell expands it, so any indirection reads as "wrong simulator."
**What better looks like:** Always pass the literal UDID in flowdeck commands. Put the variable inside a helper script instead — the hook only sees the script invocation.

### 2026-08-03 — Found a live Readwise API token shipped inside the app binary

**What happened:** While isolating the test vault I traced the auto-sync to `BundleReadwiseBundledTokenProvider`, which reads `ReadwiseDefaultToken.txt` out of `Bundle.main` and seeds it into the keychain on first launch.
**Why this matters:** A working Readwise token is extractable from any build, including TestFlight distributions. It is not in git, so normal secret scanning would not catch it. Documented in `.claude/migration-spec/04-migration-risks.md` with a recommended fix (require user-entered token; `#if DEBUG` + untracked file for local dev; rotate the current token).
**What better looks like:** Treat "state that survives a device erase" as a signal to check the build inputs, and audit bundled resources for credentials the same way we audit committed files.

### 2026-08-03 — Declared iPad screens "equivalent to iPhone" without checking

**What happened:** I captured only 6 iPad states and justified it in the spec as a deliberate "delta-only" scope, claiming the uncaptured screens were equivalent to iPhone. Eugene asked whether that was really OK. It was not — checking took ten minutes and found four genuine deltas I had asserted away: chat and settings present as **inset form sheets** at regular width, search uses `presentationSizing(.page)`, and AI Chat is reached from the sidebar More menu because the iPad dock has no chat button. I had also written that the iPad editor dock was "absent" when it is present, centred, and compact.
**Why this was wrong:** I dressed an untested assumption in the language of a deliberate decision. "Delta-only" is a legitimate scope, but only once you have verified what the deltas are — otherwise it is just unexamined coverage with a confident label. For a document whose entire purpose is to be the migration's source of truth, a wrong assertion is worse than an admitted gap.
**What better looks like:** Never write "equivalent to X" about something not observed. Either capture it, or list it explicitly as unverified. When scoping coverage down, the reason must be evidence ("I checked, it matches"), never inference ("it probably matches"). The spec now says this in its own words so the same trap does not catch the migration.

### 2026-08-03 — macOS verification pass found a shipping bug the spec would have hidden

**What happened:** After the iPad correction, Eugene asked for the same pass on macOS. Verifying the `NSTextView` editor against the `UITextView` baseline found that **todo checkboxes do not render on macOS at all** — `TodoLayoutFragment.draw` only calls `super.draw`, and `TodoMarkerButton` / `todoMarkerButtons` / `todoMarkerOverlayLayout` are all inside `#if os(iOS)`. Indent and strikethrough still apply because they come from shared paragraph styling, so the bug reads as "todos look plain" rather than "todos are broken." On macOS a todo can only be toggled by editing raw markdown.
**Why this matters beyond the bug:** my original spec would have shipped a UAT checklist that scored the RN build against a defective reference — a correct RN implementation would have "failed" macOS todos, or a matching-but-broken one would have "passed." Both outcomes are worse than having no row at all.
**What better looks like:** when two platforms share an abstraction but have different concrete backends (TextKit 2 on `UITextView` vs `NSTextView`), treat rendering parity as something to test, never to assume — the shared upper layer is exactly what makes divergence invisible. And when building a reference baseline, verify the baseline itself is correct before asking anyone to match it. A spec that faithfully documents a bug propagates it.

### 2026-08-03 — Overclaimed a bug's scope; the hit-testing existed all along

**What happened:** After finding that macOS todo markers never render, I wrote in the spec that "on macOS a todo can only be toggled by editing raw markdown" and added a UAT row saying there was no toggle affordance at all. When I later fixed the rendering, I checked the macOS click path and found `todoMarkerHitRect` → `toggleTodoMarkerAtPoint` → `todoBlock(containingMarkerPoint:)` already implemented. The hit target was there; it was just invisible.
**Why this was wrong:** I inferred the absence of toggling from the absence of a *drawn* marker plus a parity-checker hit on `toggleTodoForSelectedLines` being iOS-only. Neither actually establishes that macOS cannot toggle — the checker pairs by name, and macOS names its equivalent differently. I extrapolated from one confirmed fact (no glyph) to a second, unchecked one (no interaction), and wrote both with the same confidence.
**What better looks like:** state exactly what was observed and no more. "The marker does not render" was verified; "todos cannot be toggled" was not. When a tool reports a gap, check whether the other side implements the same behaviour under a different name before calling it missing. Corrected in the spec, and the click path is now explicitly marked expected-to-work-but-unverified rather than either broken or fine.

### 2026-08-03 — Burned ~35 minutes on a hung test run instead of scoping the verification

**What happened:** To check my todo fix for regressions I launched the *entire* iOS suite (250+ tests). It hung — 31 minutes with zero file activity in the test devices — after three earlier invocations had already been killed and left contending processes behind. I polled it repeatedly before checking whether it was actually progressing.
**Why this was wrong:** two mistakes. First, I reached for the broadest possible suite when my change touched exactly three symbols (`TodoMarkerRenderer`, `TodoLayoutFragment`, `TodoMarkerButton.draw`); the two suites that could plausibly regress ran in ~60s each. Second, I treated "process still alive" as "still working" for half an hour — `find -newermt` on the test devices would have shown it stalled within a minute.
**What better looks like:** scope the regression run to the suites that touch the changed code, then run the full suite once in the background if wanted. When waiting on a long job, check for *progress* (file mtimes, log growth), not just liveness. And kill leftover `xcodebuild test` processes before starting a new one — flowdeck runs share DerivedData and a stale run will deadlock the next.
