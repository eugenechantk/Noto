## Log

### 2026-08-05 — Data audit should have come before GUI repro

**What happened:** Bug report was "some inline images cannot be rendered … like the one in the
AI photo/video/creative generation note". I spent ~40 minutes building the macOS app, driving it
with axdriver, resizing windows, and screenshotting — and never reproduced it on that note.
A Python reimplementation of the parser rules run over the whole vault took 2 minutes and found
587 non-rendering image lines with a clear dominant cause (caption text trailing the link).

**Why this was wrong:** the word "some" in a bug report means *a subset of the data set fails*.
When the failing behavior is a pure function of file content, enumerating the content against the
code's rules is both faster and more complete than driving the UI. GUI repro is for confirming a
specific instance, not for discovering which instances fail.

**What better looks like:** when a report says "some X don't work" and X is derived from files
the code parses, first extract the rule from the code, reimplement it in a throwaway script, run
it over the whole corpus, and classify the failures. Then use the GUI to confirm one example from
the largest failure class. Add this as a step in `/ios-debug-flow` Step 1 alongside the existing
"perceptual vs literal symptoms" guidance.

### 2026-08-05 — flowdeck macOS run blocked by the simulator-isolation guard

**What happened:** `flowdeck run --platform macos` was rejected by
`~/.claude/hooks/flowdeck/flowdeck-guard.sh` with "this command targets the shared/config
simulator", and it created and booted an iPhone simulator this session never needed.
The guard's own text elsewhere names the right form: `flowdeck run --simulator none`.

**Why this was wrong (in the system, not the run):** the guard does not exempt macOS targets, so a
macOS build costs a wasted simulator boot and a round trip to read the guard source.

**What better looks like:** the guard should skip the isolation check when the command carries
`--platform macos`, `--simulator none`, or `-D "My Mac"`. Until fixed, always invoke macOS runs as
`flowdeck run --simulator none` / `flowdeck build -s Noto-macOS -D "My Mac"`.

### 2026-08-05 — macOS local-build signing recipe from memory worked first try

**What happened:** The build failed on `match AppStore com.eugenechan.Noto` not matching the macOS
platform. The `project-macos-local-build-signing` memory had the exact recipe (temp xcconfig with
Automatic signing + team, ASC key decoded from `fastlane/.env.default`, pass through
`--xcodebuild-options`). Applied verbatim, built clean.

**Why this matters:** this is the system working as intended — a previously-costly dead end
resolved in one step. The underlying pbxproj issue (Debug configured for distribution signing) is
still open and still costs this xcconfig dance on every fresh checkout.

**What better looks like:** land the real fix — revert Debug to Automatic signing in the pbxproj
and apply match signing at gym/export time in the Fastlane lane.

### 2026-08-05 — Quoted an impact number from an unvalidated categorisation

**What happened:** I reported "431 trailing text after `)`" to Eugene, then on a second pass found
that bucket was two unrelated causes (262 caption text + 154 nested-paren/extension-less URLs).
I then projected the fix would recover ~223 lines. After implementing it, the measured recovery
was **73**. The gap came from `[![](img)](link)` shapes — a link wrapping an image — which my
first-`![`-wins categoriser had miscounted into the extension-less bucket.

**Why this was wrong:** I presented a derived number as a finding without checking that the
categoriser's parsing matched the real code's parsing on nested shapes. A bad denominator drove
a scoping decision ("this category is cheap, do it first"), and I stated it to Eugene as fact.

**What better looks like:** when a script reimplements production logic to size a problem,
(1) validate it against the real parser on the tricky shapes before quoting counts, and
(2) measure impact by re-running the audit *after* the fix rather than projecting it. The
before/after run (585 → 512) is the number that should have been quoted in the first place.
