### 2026-08-11 — Local DNS resolver silently lies

**What happened:** After creating the `noto` CNAME, `dig` returned NXDOMAIN from both of the zone's
authoritative nameservers for several minutes. I re-checked the dashboard, polled for a minute, and
started diagnosing a Cloudflare-side failure. The record was live the whole time — DNS-over-HTTPS to
both Cloudflare and Google returned `Status 0` with correct A records immediately.

**Why this was wrong:** The tell was in the first response I looked at: `flags: qr rd ra` with no
`aa`. An authoritative server sets `aa`; a resolver sets `ra`. Something on this machine's network
intercepts port-53 traffic and answers on behalf of whatever server you name, including stale
NXDOMAIN for new records. `dig @<authoritative-ns>` is therefore not trustworthy here.

**What better looks like:** On this machine, verify DNS with DoH first, not `dig`:
`curl -s 'https://dns.google/resolve?name=<host>&type=A'`. Use `dig` only for a quick positive
signal; never trust a negative from it. Check for `aa` in any answer claiming to be authoritative.

### 2026-08-11 — Read the wrong entitlements slot on a simulator build

**What happened:** Ran `codesign -d --entitlements` on the built simulator `.app`, got an empty
dict, and told Eugene the entitlement hadn't been applied. It had — simulator builds put the real
entitlements in `Noto.build/<config>/Noto.build/Noto.app-Simulated.xcent`, and the main slot is
legitimately empty.

**Why this was wrong:** I reported a conclusion from one tool reading without checking whether that
tool reads the slot the simulator actually uses. It sent me toward an imagined signing problem.

**What better looks like:** For simulator builds, read `*-Simulated.xcent` in the intermediates dir,
not `codesign -d` on the bundle. Worth remembering as a general rule: simulator ≠ device for
anything signing-related, in both directions.

### 2026-08-11 — flowdeck-guard hook does literal string matching

**What happened:** Wrote `SIM=0F07...; flowdeck ui simulator open-url -S "$SIM"` and the guard hook
blocked it, reporting the target as literally `'$SIM'`. The hook inspects the raw command text
before shell expansion.

**Why this matters:** Costs a full round-trip every time, and the error message looks like a real
isolation violation rather than a quoting artifact.

**What better looks like:** Always inline the literal UDID in flowdeck commands in this repo. Never
put it in a shell variable.

### 2026-08-11 — Verified the fallback page only on first load

**What happened:** Checked the "Open in Noto" page by loading it once with a valid fragment, saw it
render correctly, and moved on. Only when I navigated to a *second* link in the same tab did I
discover the script ran once on load and never on `hashchange` — the page kept showing the previous
note, with the button still pointing at it. That would have opened the wrong note.

**Why this was wrong:** I verified the happy path in isolation and treated it as proof the component
worked. The bug lived in the transition between states, which single-shot verification cannot see.

**What better looks like:** For any component driven by URL state, always test the *second*
navigation, not just the first. More generally: when verifying, exercise at least one state
transition rather than one state.

### 2026-08-12 — Repeated a feature doc's claim without verifying it

**What happened:** `.codex/feature/noto-deep-links.md` listed, as completed, that the Readwise digest
worker appended Noto deep links, with three named test files as evidence. I carried that into my own
residual-risks section as "the worker still emits `noto://`" — implying working code that merely used
the old shape. When Eugene asked me to update it, the truth was that no deep-link code had ever
existed there and two of the three named test files did not exist at all.

**Why this was wrong:** I treated a checked-off success criterion in a doc as evidence of shipped
behaviour. Docs record *intent at time of writing*; only the code and its tests record what shipped.
I also stated the risk with more confidence than my evidence supported — I had grepped `~/dev` once
for `noto://`, got nothing, and interpreted that as "the repo is elsewhere" rather than the simpler
"the feature isn't there."

**What better looks like:** Before citing a prior feature doc's claim, spend the 30 seconds to grep
for the symbol it says exists. When a search for the expected code comes back empty, treat
"it was never built" as the leading hypothesis, not the last one. And when writing a residual risk
about a component I have not opened, say "unverified" rather than asserting its behaviour.

**Systemic fix worth making:** feature docs in this repo should distinguish criteria that were
*verified with named evidence* from criteria that were *planned*. The universal-links doc now does
this with an explicit Verification Evidence table; older docs do not.
