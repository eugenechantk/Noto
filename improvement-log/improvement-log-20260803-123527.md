### 2026-08-03 — Chased the tag-system work before checking basic file readability

**What happened:** Given "clicking a note does not show it on the editor view" on macOS,
I reproduced, sampled the process, saw the read blocked in `NSFileCoordinator`, and then
spent a full build cycle adding a `NOTO_DISABLE_TAG_SCAN` kill-switch to A/B the
uncommitted `TagController` work (which reads every `.md` in the vault). It was
disproved. The decisive test — `head -c 200 <note>.md` from the shell with the app not
running, then `ls -lO` — took ~30 seconds and pointed straight at iCloud eviction
(`dataless`) plus a pegged `fileproviderd`.

**Why this was wrong:** The stack already said the thread was parked in `read()` on a
vault file. The cheapest next question is "can *anything* read this file?", not "which
of my recent code changes caused it?". Suspecting the newest diff is a decent prior, but
it should not outrank a 30-second environment probe.

**What better looks like:** When a stack shows a blocked filesystem syscall, immediately
test the same read from the shell with the app killed. If it also blocks, it is an
environment/OS problem — stop bisecting app code. For a synced vault (iCloud/Dropbox),
also check `ls -lO` for the `dataless` flag and the provider daemon's CPU before
touching app code.

### 2026-08-03 — Runtime-first macOS debugging worked (keep)

**What happened:** Followed the `macos-debug-runtime-first` memory: built, ran, enabled
DebugTrace, then `sample`d the live process. The trace showed `loadNoteContent` starting
and never finishing, and the sample showed exactly which frame was parked. Root cause was
visible within a few minutes of the app being up.

**Why this worked:** The code reads perfectly correctly — "try a real read first" is the
documented, intentional design. Nothing in static reading suggests it can block forever.
Only the runtime stack shows it.

**What better looks like:** Keep leading with build → run → DebugTrace → `sample` for any
macOS "it just doesn't do anything" report. Add the shell-side filesystem probe as the
step right after the sample points at I/O.
