### 2026-06-03 — Appium Mac2 verification blocked by macOS Accessibility permission

**What happened:** Fixed a macOS editor bug (note-link click didn't switch the editor). Build passed. Tried to verify at runtime via the `macos-test` skill (Appium + appium-mac2-driver). The Mac2 driver's WebDriverAgentRunner failed with exit code 65 / "Timed out while enabling automation mode." This is a macOS Accessibility permission gate — the terminal/host process running xcodebuild needs to be granted Accessibility (and likely Automation) permission in System Settings → Privacy & Security. Granting it requires manual user action, so all synthetic-input verification paths (Appium, cliclick, System Events) are blocked the same way.
**Why this matters:** macOS UI verification is a stated requirement ("don't consider a UI/UX task complete without visual confirmation"), but the automation stack can't self-bootstrap without a one-time permission grant. This will recur for every macOS UI verification until the permission is granted.
**What better looks like:** (1) Document the one-time setup: grant Accessibility permission to the terminal/host app that launches Appium so Mac2 automation works headlessly. (2) Consider a project script that checks this permission up front and fails fast with the exact System Settings path, instead of discovering it mid-run via a code-65 build failure. (3) For unblocked-permission environments, prefer reading the editor's AXTextArea value before/after a coordinate click as the verification signal.

### 2026-06-03 — macOS UI verification: lldb ObjC inspection beat screenshots/logs

**What happened:** Implementing the macOS soft scroll-edge effect, I needed to confirm (a) whether SwiftUI's unified toolbar exposes titlebar accessory view controllers, and (b) that my added accessory carried `.soft`. `screencapture` couldn't isolate the Noto window (it stayed behind other windows; `osascript ... activate` was flaky/permission-limited), and `os_log`/`log show`/`log stream` surfaced zero lines for the app's subsystem in this environment. What worked decisively: `lldb -p <pid>` + ObjC expressions to read `[[window titlebarAccessoryViewControllers] count]`, the accessory `identifier`, and `preferredScrollEdgeEffectStyle == [NSScrollEdgeEffectStyle softStyle]`. This proved SwiftUI ships 0 accessories (so "set on existing" was a no-op) and that the final code installs exactly 1 soft accessory on launch.
**Why this matters:** For macOS AppKit-state questions ("did this property get set on the real window?"), live lldb introspection is faster and more reliable than visual capture or logging — especially when window-management and TCC permissions block the usual paths. It also caught a real bug: the first implementation set the style on existing accessories, of which there were none.
**What better looks like:** When verifying AppKit runtime state on macOS, reach for `lldb -p` ObjC introspection early. Gotchas: cast every message send on `id` to its return type; `NSMakeRect`/`NSLayoutAttribute*` constants aren't available (use struct literals / raw enum ints); multi-arg `stringWithFormat:` fails the expr parser — print values via separate `-o` commands. Launch via `open <app>` (not `flowdeck run`) when you need attach to succeed.

### 2026-06-03 — macOS editor lag root cause + fix

**What happened:** User reported lag loading notes, selecting words, and typing — persisting in a Release build. Investigation (skill: ios-performance-profiling). Two causes:
1. Earlier installs were Debug (install_macos_app.sh hardcodes Debug); Debug TextKit2 styling is very slow. Rebuilt Release.
2. Real hot path: on every keystroke AND every selection/cursor change, the macOS editor re-ran whole-document parses — `MarkdownSemanticAnalyzer.renderableBlocks(in: wholeDoc)` and `HyperlinkMarkdown.matches(in: wholeDoc)` — via restyleTextPreservingSelection / applyDivider / applyHyperlink / refreshDividerLineViews. Cost scales with note size; the user's Captures notes are up to 265 KB / 2,136 lines, so selecting/typing did O(n) regex+parse work per event. (Find, page-mention, and typing-attributes paths were checked and found cheap: empty-query early return, line-scoped, paragraph-scoped respectively — not the cause.)
**Fix:** Memoized the two whole-document parses in the macOS view controller, keyed on a `documentEditVersion` bumped in `textStorage(_:didProcessEditing:)` on `.editedCharacters` (renderableBlocks cache also keyed on collapsedXMLTagRanges). Selection/cursor changes (no text edit) now reuse the cached parse instead of re-parsing; edits recompute once and reuse within the same event. macOS only (reported platform).
**Verification gap:** Could NOT get a clean before/after number in this environment — every measurement path was blocked: GUI window capture flaky (window behind other apps / wrong Space), os_log never surfaced for the app's subsystem, lldb Swift expr can't see app-internal types from an idle frame, in-app probe never fired because macOS state restoration restores editor text WITHOUT calling applyText (and sandbox redirects /tmp), and the unit-test target won't compile (pre-existing `rebuildIndex` arg error in SearchIndexControllerTests). Diagnosis is from call-chain reading + real input size; user's large notes are the definitive before/after.
**What better looks like:** (1) Add a Release flag to install_macos_app.sh. (2) Fix the broken test target so headless XCTest performance tests can run (the right measurement surface here). (3) Consider scoping the per-event divider/hyperlink *attribute application* (not just the parse) to the edited/visible range for a further win on very large notes. (4) Mirror the memoization to the iOS/iPadOS editor (same code shape) since iPad regular/split reuses the editor.

### 2026-06-03 — Consolidated the drifted iOS/macOS editor rendering

**What happened:** Root cause of the macOS editor lag was architectural drift: the editor has ONE shared styling engine (`MarkdownTextDelegate`, `MarkdownSemanticAnalyzer`, etc.), but the reveal/restyle/apply-attributes *coordination* was duplicated in each platform's view controller (`UIViewController` vs `NSViewController`). iOS had been optimized to scope rendering to the affected line ranges; macOS still did whole-document parses + attribute application on every keystroke and selection change → lag on large notes. User chose to consolidate (not copy-paste).
**Fix:** Extracted the coordination into a shared `MarkdownRevealRenderingHost` protocol + extension (all logic runs on `NSTextStorage`, common to UIKit/AppKit). Both controllers conform via a handful of primitives (`renderTextStorage`, `renderSelectedRange`, `renderMarkdownDelegate`, `refreshTypingAttributes`). Deleted ~16 duplicated methods from each controller; macOS now runs the exact same incremental, affected-range-scoped rendering iOS uses. Net −24 lines despite adding the shared layer. Also removed the macOS-only memoization I'd added earlier (superseded by the shared incremental approach).
**Verification:** Fixed a pre-existing test-target compile error (`SearchIndexControllerTests` missing `rebuildIndex`) to unblock the unit tests as a safety net. The 45 `TextKit2MarkdownLayoutTests` (bullets, dividers, hyperlinks, todos — exactly the rendering consolidated) pass on iOS after extraction, proving the shared logic preserves behavior; macOS then runs that same proven code. Both platforms build; macOS Release installed. One unrelated lifecycle test fails (`pageMentionSuggestionRowsKeepHorizontalInsetInsidePopover` — popover layout, headless-window-sensitive, pre-existing). macOS rendering *feel* still needs the user's eyes (macOS UI can't be auto-verified in this env), but it's now the same test-verified shared implementation as iOS.
**What better looks like:** When a "shared" component keeps two platform controllers, put cross-platform logic behind a protocol extension from the start so it can't drift. The `NSTextStorage`-level logic was always shareable; only `selectedRange`/`textStorage`-optionality/colors differ.
