### 2026-08-30 — Theorized instead of testing against the real vault

**What happened:** After failing to reproduce on a 6-note seeded vault, I spent several rounds
reading code and ranking hypotheses (CJK tokenizer, RRF fusion starvation, dataless iCloud
files) before realising Eugene's real 1131-note vault sits on this Mac at
`~/Library/Mobile Documents/com~apple~CloudDocs/Noto`, along with the macOS app's live search
index — both directly queryable.

**Why this was wrong:** Two commands (`sqlite3` against the live index, `rsync` the notes into
the simulator container) falsified three hypotheses at once and were available from the start.
Reading code to rank guesses is what you do when you cannot observe; here I could observe.

**What better looks like:** For any "feature X doesn't work on my real data" report, locate the
real data first and run the failing operation against it. On this project: the vault path is in
`defaults read com.eugenechan.Noto` → `vaultDirectPath`, and the live indexes are under
`~/Library/Containers/com.eugenechan.Noto/Data/Library/Application Support/Noto/SearchIndexes/`.
Copying the real vault into a simulator container is a ~30s operation and is the highest-signal
first move.

### 2026-08-30 — `cd` persisted across Bash calls and misdirected a device build

**What happened:** Ran `cd Packages/NotoSearch && swift test`, then later `flowdeck run -D
"Eugene's iPhone"`. FlowDeck resolved DerivedData as `NotoSearch-88df8dbb` because the working
directory was still the package, not the repo root.

**Why this was wrong:** The Bash tool's working directory persists between calls. I treated
each call as independent.

**What better looks like:** Use subshells — `(cd Packages/NotoSearch && swift test)` — or pass
absolute paths, so no call can leave the shell somewhere the next one does not expect.

### 2026-08-30 — Typed into an unfocused search field three times

**What happened:** `flowdeck ui simulator tap "Search notes"` reported success but did not
focus the SwiftUI `.searchable` field, so the subsequent `type` went nowhere. I only noticed
after reading a screenshot that still showed the previous query. This recurred when a
navigation tap landed on the keyboard accessory toolbar overlaying the tab bar.

**Why this was wrong:** I chained tap → type → screenshot instead of tap → verify → type. The
flowdeck skill states this explicitly ("verify after EVERY UI action").

**What better looks like:** For SwiftUI `.searchable`, tap the field by **point** (the bar sits
at y≈92 when active, y≈139 when idle) and confirm the caret before typing. When a keyboard
toolbar is up, `hide-keyboard` first — the tab bar sits ~6pt above where it appears to.

### 2026-08-30 — No device-side debugging path for Eugene's iPhone

**What happened:** Needed runtime evidence from the physical iPhone (iOS 26.6). `flowdeck
device list` shows it over USB, but `xcodebuild` reports "no destination matching" — Xcode
26.3 is older than the device's OS. Fell back to asking Eugene to read a number off screen.

**Why this matters:** Any bug that only manifests on his real device (iCloud eviction, real
vault scale, background suspension) is currently un-instrumentable. That is a standing gap,
not a one-off.

**What better looks like:** Either keep Xcode within one minor of the device OS, or design
these features so the app self-reports its state in the UI (which is what the bug-030 fix
does). Prefer the second — it helps Eugene as much as it helps debugging.

### 2026-08-31 — Two "broken feature" reports were both silent degradation

**What happened:** Bug 030 ("search doesn't show matching notes") and bug 031 ("AI summary
only returns snippets") were both features *degrading quietly* rather than failing. Search
fell back to an incomplete index and said "check the spelling"; the summary fell back to
offline extractive highlights and said only "Offline highlights". In both cases the app knew
exactly what had gone wrong and showed the user something that implied a different problem.

**Why this matters:** Each cost a long investigation that started from a false premise — I
looked for a broken tokenizer and a broken OpenRouter route, neither of which existed. A one-
line status in the UI would have made both reports self-diagnosing.

**What better looks like:** When adding a fallback tier, treat "which tier am I in, and why"
as part of the feature, not as debug output. Concretely: any `catch` that substitutes a
degraded result must carry the reason into the view model, and the view must render it. Apply
this to the remaining fallbacks in this app — semantic-search degradation to keyword-only, and
iCloud read failures.

### 2026-08-31 — Guessed at SwiftUI search-bar placement instead of reading the docs

**What happened:** Eugene asked for the search bar flush to the top. I tried
`.toolbar(.hidden, for: .navigationBar)` (hid the search field too), then default
`.searchable` placement (no change), then hand-rolled the field — three build/run cycles of
roughly two minutes each.

**Why this was wrong:** The project CLAUDE.md is explicit that iOS 26 layout/API behaviour must
be checked against live Apple docs rather than training knowledge, precisely because these
APIs changed. I had the rule in context and skipped it.

**What better looks like:** For any iOS 26 chrome question (`searchable`, toolbars, Liquid
Glass, tab roles), fetch the current doc first. One fetch would have beaten three builds — and
would have settled whether `Tab(role: .search)` is the intended iOS 26 pattern here, which I
still have not confirmed.
