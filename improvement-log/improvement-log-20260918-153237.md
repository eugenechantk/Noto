### 2026-09-18 — flowdeck-guard did not isolate the first run

**What happened:** `flowdeck run -s Noto2 --json` built and launched on the saved-config simulator `D69C6DC8` ("iPhone 17"), the shared one. The PreToolUse guard in `~/.claude/settings.json` is present but did not print a UDID or block the command. `CLAUDE_SESSION_ID` was also unset in the shell, so the improvement-log session id fell back to a timestamp.
**Why this was wrong:** Project CLAUDE.md: never test on the shared simulator; the guard is supposed to make that impossible. I trusted the guard instead of checking `flowdeck simulator list` for a `cc-` sim first. The app was installed on the shared sim (stopped, not uninstalled — could hold Eugene's own data).
**What better looks like:** On the first flowdeck run/test of a session, confirm the guard printed a `cc-<sid>` UDID. If it did not, provision `cc-<8 chars of session id>` explicitly before running anything, and log the guard miss. Worth a `/self-improve` look at why the hook did not fire under bypass-permissions mode.

### 2026-09-18 — Syncthing conflict copies were silently breaking the Noto build

**What happened:** `Noto/Editor/BlockEditingCommands.sync-conflict-20260824-…swift` and `TextKit2EditorView.sync-conflict-…swift` (untracked, dated 2026-08-23, from before the `NotoShared/` move) were still inside the synced `Noto/` group, so Noto-iOS compiled the editor twice and failed with `ambiguous use of 'requestShowFind()'`. They had been in `git status` since at least 2026-08-24 and nobody caught it because recent work only built `Noto2`.
**Why this matters:** A Syncthing conflict file inside a filesystem-synchronized Xcode group is compiled like any other source. Same root cause family as the `flowdeck-guard.sh` overwrite on 2026-09-11.
**What better looks like:** Treat `*.sync-conflict-*` files under any compiled folder as build breakers: move them out (kept in `.claude/sync-conflicts/` here) and tell Eugene. Worth a global rule or a pre-build check that greps for `sync-conflict` under source folders.

### 2026-09-19 — Noto-macOS scheme silently broken since the NotoShared move

**What happened:** A compile check of `Noto-macOS` (run to prove the new drain compiles for macOS) failed on `NotoShared/Views/EditorContentView.swift:23: cannot find type 'EditorKeyboardToolbarStyle'` — the property is declared outside the `#if os(iOS)` block that defines the type. Last touched in `af25747` (2026-08). Not caused by this session; only the one error, so the new code is fine on macOS.
**Why this matters:** `NotoShared/` must build for both iOS-only Noto 2 and multiplatform Noto (README rule), but nothing enforces it — sessions build `Noto2` only. `scripts/check_platform_parity.py` exists; unclear whether it would catch this.
**What better looks like:** Fix is a one-liner (wrap the property or move the type out of `#if os(iOS)`), left for a separate change so this feature stays scoped. Longer term: a cheap pre-commit or session-start compile of `Noto-macOS` with `CODE_SIGNING_ALLOWED=NO`, which sidesteps the match-signing problem entirely (this run proved that flag works for local macOS builds).

### 2026-09-19 — Reading share-extension logs took two blind rounds

**What happened:** `flowdeck logs` only streams FlowDeck-launched app processes, so the share extension's `Logger.info` lines were invisible. I fell back to `xcrun simctl spawn <udid> log show` but the first two queries returned only UIKit noise: `log show` omits `.info`/`.debug` os_log entries unless `--info --debug` is passed, and a `process ==` predicate did not match the lines my `subsystem ==` predicate later did.
**Why this matters:** Each blind round meant another share-sheet drive on the simulator (~1 min) with no signal. The extension had actually crashed (`~/Library/Logs/DiagnosticReports/Noto2ShareExtension-*.ips`) and the crash report was the fastest answer.
**What better looks like:** For any app-extension debugging on the simulator: (1) check `~/Library/Logs/DiagnosticReports/<ExtensionName>-*.ips` first, (2) `xcrun simctl spawn <udid> log show --last 3m --info --debug --predicate 'subsystem == "<extension bundle id>"' --style compact`. Candidate for `reference_flowdeck_quirks`. Also worth asking FlowDeck for a `logs --process` option.

### 2026-09-19 — Tested the deep-link "open note" from one starting state only

**What happened:** My manual pass exercised "Add notes in Noto 2" with Browse at its root. The auditor tried it with a note already open in Browse and the editor stayed on the old note (2/2). Root cause: `path = [destination]` replaced a one-element stack with another one-element stack, and SwiftUI kept the same `NoteScreen` (its `@State` session came from the old note). Fix: `.id(destination)` on the destination view.
**Why this matters:** Navigation hand-offs have at least three starting states — root, same screen already pushed, different screen pushed — and only the first was covered. This is the exact class of bug the `/ios-development` skill flags as "navigation wiring, not provable by Swift tests"; the independent audit earned its keep here.
**What better looks like:** For any "open X from elsewhere" feature, enumerate the destination's stack states before verifying (root / X already open / another item open / tab not yet created) and drive at least the "already open" case. When a SwiftUI `NavigationStack` path is *replaced* rather than appended, key the destination view by value.
