### 2026-06-06 — Rebuilt a native macOS sidebar by hand instead of using NavigationSplitView's Liquid Glass

**What happened:** For the macOS floating glass sidebar I replaced `NavigationSplitView` with a custom `ZStack`/`HStack` of a hand-rolled glass panel. It cost me: the traffic lights vanished (my panel drew over them), the sidebar wasn't resizable, the width was a fixed 230, and the "glass" was a static approximation. The user corrected all of it: "these should all come with the native sidebar + Liquid Glass, like Apple apps." Reverting to `NavigationSplitView` + `navigationSplitViewColumnWidth(min:ideal:max:)` restored floating Liquid Glass, resizing, and traffic lights in one move — and deleted code.
**Root cause (two layers):** (1) I presented a scope fork ("custom panel needed for the floating look") and built on it WITHOUT first checking whether the platform provides the behavior natively. On macOS 26 (Tahoe) / iOS 26, `NavigationSplitView` sidebars are Liquid Glass, floating, and resizable by default. (2) This violated the implement-claude-design rule already in the skill: "platform-native APIs over re-creations." A web mock's "floating glass panel" is almost always the NATIVE sidebar on the new OS — not a thing to rebuild.
**What better looks like:** Before building any custom chrome (sidebar, toolbar, window, tab bar), FETCH THE LIVE DOCS (WWDC + HIG + API) for the target OS and check what the native container already provides — *especially* on iOS 26 / macOS 26 where Liquid Glass is native. Default to the native control + theme its content; only go custom when the native control genuinely can't express the design. Don't offer the user a "custom vs native" fork until I've confirmed the native option's actual capabilities. Saved as [[reference_apple_native_chrome_first]].

### 2026-06-05 — Design's translucent glass produced a two-tone seam; user chose uniform solid dark

**What happened:** After matching the design's translucent sidebar glass (`rgba(34,38,46,0.55)`+blur), the sidebar showed TWO shades: lighter glass at the header/bottom vs darker rows region. Root cause: `DirectoryContentListView`'s `.background(AppTheme.sidebarBackground)` (iOS `0x111113`, opaque) paints over the glass in the List's frame, while the header + bottom inset show the glass directly → a visible seam. User: "there should just be the dark gray color in the list." Resolved by making the whole iOS sidebar one uniform solid `AppTheme.sidebarBackground` — intentionally dropping the design's translucent glass for uniformity (offered the translucent-uniform alternative).
**Lesson:** A translucent surface from a Claude Design will seam against any opaque sub-view background (List/ScrollView row bg) layered on top. Before adopting design glass on a container, audit what its children paint opaquely — either clear ALL child backgrounds so the glass is the single layer, or go uniform-solid. Don't apply glass to the container and leave an opaque List inside.

### 2026-06-05 — Substituted a bare system Material for a design's tinted glass

**What happened:** The iPad sidebar in the design is `background: rgba(34,38,46,0.55)` + `backdrop-filter: blur(50px) saturate(1.8)` — a DARK slate glass. I implemented it as `.ultraThinMaterial`, which in dark mode renders as a LIGHT frosted gray. User: "the colors are not right." I pulled the design's computed styles from the live render (confirmed the exact rgba) and fixed it by layering the slate tint over the material: `ZStack { Rectangle().fill(.ultraThinMaterial); NotoTheme.sidebarGlass }` (matches the CSS model: blur the backdrop, paint rgba on top).
**Why this was wrong:** A "glass" surface in a Claude Design almost always has two parts — a blur AND a semi-transparent color tint. A bare system material only supplies the blur (and the wrong base tint). Reading just "it's glass → use ultraThinMaterial" drops the design's actual color.
**What better looks like:** When a design surface uses `backdrop-filter` + `background: rgba(...)`, reproduce BOTH: a Material (or blur) for the backdrop and the exact rgba painted on top. Pull the rgba from the rendered DOM's computed style — don't eyeball or assume a system material matches. Tokenize it (`NotoTheme.sidebarGlass`) so it's reusable + auditable.

### 2026-06-04 — Frontmatter-only edits silently skipped by a body-only save guard

**What happened:** Implementing Properties editing, edits updated `session.content` (the list reflected them) but never reached disk — file mtime never changed, even after switching to a synchronous persist. Spent time suspecting the editor's UITextView ownership / alert focus before finding it.
**Root cause:** Two layers — `MarkdownNoteStore.saveContent` AND `NoteRepository.saveContent` (NotoVault) — both did `guard stripFrontmatter(existing) != stripFrontmatter(new)` and returned `didWrite: false` when only the frontmatter changed. By design they treat metadata-only diffs as no-ops (to avoid bumping `modified` on no body change). Properties editing is exactly a frontmatter-only change, so every write was skipped.
**Fix:** Threaded a `force: Bool` flag through `NoteEditorSession.persistEditorText` → `VaultController.save` → `MarkdownNoteStore.saveContent` → `NoteRepository.saveContent`. A new `session.applyExternalContentEdit(_:)` persists frontmatter edits with `force: true`. Verified: swipe-delete removes a key + preserves all others; date edits persist.
**What better looks like:** When an edit "updates the view but never persists," check the SAVE path's change-detection guard early — and verify persistence by the on-disk file (mtime/content), never the in-memory view. Note `flowdeck` cannot type into iOS *alert* text fields, so verify alert-driven value edits via deterministic paths (delete, picker) or real-device testing.

### 2026-06-04 — Properties editing write-back doesn't persist through the live editor

**What happened:** Built a fully-editable Properties sheet (add/edit/delete frontmatter via `EditableFrontmatterDocument`) that applies changes with `session.content = newMarkdown; session.handleEditorChange(newMarkdown)`. The in-memory list updated correctly (rows added/removed), but nothing ever reached disk (file mtime unchanged, even after editor `onDisappear` final-persist).
**Root cause:** While the `.sheet` covers the editor, the editor's `UITextView` (the authoritative source for `latestEditorText`/persist) does not adopt the external `session.content` change — SwiftUI doesn't drive `updateUIViewController` on the covered representable. So the textview keeps the old text and wins at persist time; the frontmatter edit lives only in SwiftUI state.
**Why it matters:** Spent significant time chasing this as UI-automation flakiness (alert focus) before isolating it with a swipe-delete test + file-mtime check. The real signal was "list updates but mtime never changes."
**What better looks like:** For any feature that edits the note's text from OUTSIDE the editor (properties, AI actions, link insertion), the edit MUST go through an authoritative session write-back that updates the `UITextView` text and persists — not just `session.content`. Verify persistence by checking the on-disk file, not just the in-memory view. Decision: descoped Properties to read-only this pass; re-enable editing during the editor pass where the textview write-back path is in scope.

### 2026-06-04 — Synthetic edge-swipe is not a valid test for interactive pop

**What happened:** After hiding the system nav bar to build a custom bare-icon top bar, the edge-swipe-back stopped working. I added the standard `interactivePopGestureRecognizer` delegate fix, then tried to validate it with `flowdeck ui simulator swipe --from "2,420" --to "370,420"`. It didn't pop, twice — which looked like the fix had failed.
**Why this was misleading:** `UIScreenEdgePanGestureRecognizer` (which backs the interactive pop) ignores synthetic/programmatic swipes — it requires real screen-edge touch events. So the synthetic swipe is a guaranteed false negative regardless of whether the fix works. I nearly iterated on a working fix.
**What better looks like:** To verify an edge-pan/interactive-pop fix, don't synthesize the swipe. Instead verify at runtime that the delegate is installed and gated correctly (I added an os_log: "delegate set, stack depth=2"), and treat the on-screen back BUTTON popping as the testable affordance. Bake this into the iOS validation playbook: gesture recognizers requiring real touches (screen-edge pan, 3D-touch, some long-press) can't be proven by simulator automation; prove them by inspecting recognizer state at runtime.

### 2026-06-06 — Speculative background changes before diagnosing the macOS top-bar tint
**What happened:** User reported the macOS detail top bar was a darker shade than the editor. I tried, in order: `.toolbarBackground(.hidden)`, `window.backgroundColor`, `window.titlebarAppearsTransparent`, the SwiftUI root `.background`, the editor `.background(...).ignoresSafeArea()`, and the NSScrollView `.backgroundColor` — each a rebuild — none of which moved the measured strip color off (10,10,10). Only THEN did I run a decisive experiment (force the toolbar red) that revealed the toolbar is window-wide and the strip is the detail column's own backing, which pointed straight at the real fix (NSView extends under the toolbar + scrollView pinned to the safe-area guide).
**Why this was inefficient:** I had already pixel-sampled and knew the exact target/actual colors early. The right next move was to immediately probe the LAYERING (what view owns that strip?) with one unambiguous experiment, not to keep guessing which existing background might be the source. Each guess cost a full macOS build+launch+screenshot cycle (~1–2 min).
**What better looks like:** For "wrong color in region X" on a layered native UI: (1) pixel-sample to get exact actual vs target, (2) run ONE diagnostic that forces an unmistakable color on each candidate layer to identify which layer owns the pixels, (3) then fix that layer. Probe the hierarchy before mutating it. Also: a sleeping display silently returns all-black screencaptures — check capture brightness before trusting "no change" results.
