### 2026-09-02 — Called a failed deploy "exit 0"

**What happened:** Backgrounded the TestFlight deploy as `fastlane ... > log 2>&1` followed by
`echo "exit=$?"` and then `tail`. The harness reported the command completed with exit code 0.
fastlane had in fact died instantly: the non-login shell resolved `/usr/bin/ruby` (system 2.6)
instead of the rbenv 3.2.7 the `Gemfile.lock` pins, so `bundle` couldn't find bundler 2.4.19.
Only reading the log caught it.

**Why this was wrong:** I nearly reported a successful ship on the strength of a wrapper exit
code that described the *last* command in the script, not the one that mattered. For an
outward-facing action like a TestFlight upload, "the tool said 0" is not evidence.

**What better looks like:** Two habits. (1) `set -o pipefail` and capture the real command's
status into a named marker (`echo "FASTLANE_EXIT=$?"`) immediately after it, then grep for that
marker — which is what the successful re-run did. (2) For any deploy/publish, never report
success from an exit code alone; confirm from the tool's own output ("Successfully uploaded")
and then from the remote side. And for this repo specifically: fastlane needs
`PATH="$HOME/.rbenv/shims:$PATH"` because the tool shell is not a login shell.

### 2026-09-02 — Pre-computed the build number and failed my own verification

**What happened:** Computed the HK timestamp in my shell before launching the lane
(`202609021351`), then verified against it. The canonical Fastfile computes its *own* timestamp
when it runs, a minute later, so the ipa carried `202609021352`. `verify_testflight_build`
failed loudly with "the xcargs build number never reached the binary" — a check designed to
catch a genuine, historically-expensive bug. I briefly had to work out whether the deploy was
broken or my bookkeeping was.

**Why this was wrong:** I duplicated a value the lane owns instead of reading it back. The
skill's whole point is that the build number is injected by the lane; anything I compute
separately is a guess that happens to match most of the time.

**What better looks like:** Read the build number out of the deploy log
(`CFBundleVersion=` in the ipa-ground-truth line, or the `xcargs` line) and pass *that* to
`verify_testflight_build`. Never pre-compute a value the tool derives.

### 2026-09-02 — Version bump landed in the wrong commit

**What happened:** Bumped `MARKETING_VERSION` to 0.1.1 before starting the commit split so the
build could go out in parallel. The first commit staged
`Noto.xcodeproj/project.pbxproj` wholesale, which swept the release bump into
"Refactor: move the shared app layer into NotoShared/". The intended standalone
"Release: Noto 2 0.1.1" commit then had nothing to stage.

**Why this was wrong:** Eugene had specifically chosen a split-commit history for revert
safety, and this couples a release bump to a large refactor — reverting the refactor would
silently revert the version. I sequenced for build throughput without thinking about what the
in-flight edit would do to the staging plan.

**What better looks like:** When a change is going to be committed in pieces, make unrelated
edits *after* the split, or stash them until their own commit. If an edit must happen first
(to unblock a build), stage that file with `git add -p` / explicit path exclusion so it doesn't
ride along in an unrelated commit. Left as-is here rather than rewriting six commits of
someone else's work to relocate four lines — flagged to Eugene instead.


### 2026-09-02 — Almost filed a false bug from a dirty simulator state

**What happened:** Verifying the new four-direction gestures, I swiped up and the screenshot
showed the **Add to** sheet. I started reasoning about a mis-mapping in `DigestSwipeResolver`
— re-reading the dominant-axis logic, checking whether `@State var mode` in `DigestFileSheet`

**Why this was wrong:** I verified a step without first checking that the app was in the state

**What better looks like:** In a manual gesture-verification loop, every step that *commits*

a known state first (dismiss any sheet, confirm the card and count) instead of chaining steps
and assuming the previous one left things tidy.


### 2026-09-01 — Tests were green while two real bugs sat in the UI

**What happened:** `NotoDigest` (36 cases) + `DigestModelTests` (12 cases) all passed, and the
feature looked done. The simulator pass immediately found (a) the "Add to" note picker listing
the `inbox/` captures — including the very capture on the card, so you could append a note to
itself — and (b) a pre-filled title field with no way to clear it short of holding backspace.

**Why this matters:** Both bugs live exactly where the tests weren't: the *composition* between
a general-purpose vault API (`pageMentions` returns every note, inbox included) and a specific
screen's needs. Package tests prove the filesystem contract; they say nothing about which
inputs the screen actually feeds it. The self-append case is not cosmetic — it would have
corrupted a capture.

**What better looks like:** When a screen consumes a general-purpose query (search, mentions,
directory listing), write the "which subset does *this* screen want" filter as its own testable
function before wiring the UI, and give it a test naming the excluded case. The tell is any
call site passing a broad `limit:` and rendering the result directly. Do not treat
"package tests pass" as coverage of a screen's input selection.

### 2026-09-01 — Container accessibilityIdentifier swallowed the child buttons

**What happened:** Put `.accessibilityIdentifier("digestActionRow")` on the `HStack` holding the
three action buttons and `.accessibilityIdentifier("digestCard")` on the card `ZStack`. Both
collapsed their subtree into one element: `digestAddToButton`, `digestCreateButton`, and
`digestDiscardButton` were absent from the accessibility tree, and the whole action row reported
as a single button labelled "Add to". Only found because `tap --by-id` returned nothing.

**Why this was wrong:** This is an accessibility regression, not just an automation one —
VoiceOver would have read the three buttons as one control. The `/ios-development` skill's
identifier policy says to give every interactable control a stable identifier; a container
identifier silently voids that for everything inside it.

**What better looks like:** In SwiftUI, a container that needs its own identifier must use
`.accessibilityElement(children: .contain)` alongside it. Bare `.accessibilityIdentifier` on a
container is only correct when the container genuinely *is* one control. After adding
identifiers, dump the accessibility tree once and confirm each one is actually present before
relying on it — the tree is the contract, the source code is not.

### 2026-09-01 — `flowdeck run` wipes the data container; re-seeded three times

**What happened:** Each code fix meant `flowdeck run`, which reinstalls and clears the app's data
container — taking the seeded vault and the hand-written `inbox/` captures with it. Re-seeded
three times, and once read a screenshot of the *old* build's state before realising the UI
session had also gone stale across the reinstall.

**Why this was slow:** The project CLAUDE.md already documents this ("`flowdeck run` reinstalls
and wipes the data container") and prescribes `simulator_launch_app` for relaunch-without-
reinstall — but that only helps for relaunches, not for the rebuild-after-a-fix loop, which
must reinstall. The missing piece is that the seed is not a single command.

**What better looks like:** For any Noto 2 simulator loop, write the whole seed as one reusable
shell function/script at the start — `flowdeck run` → `seed-vault.sh` → write fixtures →
`simulator_launch_app` — instead of re-typing the capture-writing heredoc each iteration. Worth
adding an `--inbox` fixture flag to `.maestro/seed-vault.sh` so digest testing is one command.
Also: after any reinstall, restart the FlowDeck UI session and use the new paths, or you will
read a stale screen and debug a bug that is already fixed.

### 2026-09-01 — FlowDeck UI automation degraded mid-session

**What happened:** Roughly two-thirds through verification, `flowdeck ui simulator tap --by-id`
and `flowdeck ui simulator screen` both began failing with "No translation object returned for
simulator", and the capture session stopped writing `latest.jpg`. Tried restarting the session
first (correct per the skill), which did not fix it. Recovered by tapping with point
coordinates (`tap -p "x,y"`) and taking stills with `mcp__xc-testing__simulator_screenshot`.

**Why this cost time:** Went through session-restart and app-liveness checks before trying a
different capture tool, because the flowdeck skill frames `screen` as the fallback and doesn't
mention a case where flowdeck's whole accessibility bridge is the thing that's broken.

**What better looks like:** Escalation ladder when flowdeck UI automation misbehaves —
(1) restart the session, (2) confirm the app is alive, (3) **switch capture tool** to
`mcp__xc-testing__simulator_screenshot` and switch taps to `-p` point coordinates read off that
screenshot, (4) only then reboot the simulator. Point coordinates are always available: the
accessibility tree dump earlier in the session gives element frames in points, and a still
screenshot's pixel coordinates divide by the device scale.

### 2026-09-01 — Pre-existing flaky test in NotoSearch

**What happened:** The full package sweep showed `NotoSearch` failing one case — "Scheduled file
refresh debounces repeated requests" (`SearchIndexCoordinatorTests.swift:37`) — expecting a
debounced refresh call that hadn't landed. Ran the suite three more times in isolation: 7/7 pass
each time. `NotoSearch` was not touched this session (its uncommitted changes predate it).

**Why this matters:** A test that fails only under full-sweep load is a timing assumption, and
it makes the sweep untrustworthy as a regression gate — the next real regression in that package
is easy to wave off as "the flaky one".

**What better looks like:** The test should await the debounce deterministically (poll the probe
with a timeout, or inject the clock) rather than sleeping a fixed interval. Worth fixing
separately; noted here rather than fixed because it is unrelated to this feature and touching a
package mid-feature muddies the diff.

### 2026-09-01 — Dismissed a real bug because it was "consistent with the editor"

**What happened:** During simulator verification I saw that appending to `Meeting Notes.md` left
its `modified: 2026-03-15T09:00:00Z` untouched. I reasoned: `VaultMarkdown.updateTimestamp` only
knows `updated:`, the editor's own save path uses the same function, so the digest behaves
identically to the editor — a pre-existing vault-wide inconsistency, not mine. I wrote it into
the feature doc as a deliberate non-decision and moved on. The independent auditor flagged it as
a defect against SC3, which explicitly required the stamp to refresh. It was right.

**Why this was wrong:** Two errors. First, I let "consistent with existing behavior" override a
success criterion I had written myself an hour earlier — consistency with a bug is not a
justification, and if I genuinely believed the criterion was wrong I should have changed the
criterion and said so, not quietly failed it. Second, I had the evidence in hand: I *looked* at
the `modified:` line, saw it hadn't moved, and rationalised instead of investigating. The fix
took ten minutes (`stampingExistingTimestamps` refreshes whichever key exists, invents none).

**What better looks like:** When live evidence contradicts a success criterion, the default is
that the code is wrong — "matches existing behavior elsewhere" is a hypothesis to check, not a
verdict. And a criterion that gets downgraded to "residual risk" or "deliberate" mid-flight needs
an explicit note saying *this criterion is now failing and here is why that is acceptable*,
surfaced to Eugene, not buried in an implementation-details paragraph.

### 2026-09-01 — One-shot load on a screen defined by another tab's writes

**What happened:** `DigestScreen` loaded its queue with `.task { if !model.hasLoaded … }` and
offered `.refreshable` for manual reload. Both were wrong: `.task` runs once per view lifetime,
and `.refreshable` needs a scroll ancestor, which a `GeometryReader`/`VStack` is not — so
pull-to-refresh was silently inert. The auditor wrote a capture into `inbox/` with "Inbox clear"
on screen and it stayed clear through a pull and a tab round-trip. I had spotted the `.task` half
myself while reviewing, but not that `.refreshable` was dead, and had deferred the fix.

**Why this was wrong:** The tab's entire premise is "Capture writes `inbox/`, Digest reads it".
A load-once queue breaks the product loop, not an edge case. Writing `.refreshable` on a
non-scrolling view and never pulling to test it is the same failure as the accessibility
identifiers earlier this session: adding an affordance and assuming it works because the code
compiles.

**What better looks like:** For any screen that reads state another surface writes, decide the
refresh trigger *when writing the load*, not after — appearance, scene phase, and a change
notification are the three candidates, and "once" is almost never right. And SwiftUI modifiers
with structural requirements (`.refreshable` needs a scroll view, `.searchable` needs a
navigation container, `.accessibilityIdentifier` on a container needs `children: .contain`) must
be exercised once in the simulator before they count as implemented.

### 2026-09-01 — Two iCloud sync-conflict files break the Noto-iOS build

**What happened:** Grepping for frontmatter helpers surfaced
`Noto/Editor/TextKit2EditorView.sync-conflict-20260824-205538-7GKUR25.swift` (8162 lines) and
`Noto/Editor/BlockEditingCommands.sync-conflict-….swift` (1147 lines) — untracked iCloud conflict
copies of files that have since moved to `NotoShared/Editor/`. Both `Noto/` and `NotoShared/` are
synchronized groups on the `Noto` target, so both copies compile: `flowdeck build -s Noto-iOS`
fails with "invalid redeclaration of `BlockEditingCommands`", `TextSelectionTransform`,
`PageMentionQuery`, and more. Confirmed causal by moving the two files to the scratchpad —
`Noto-iOS` then built clean — and restoring them byte-for-byte.

**Why this matters:** It is not just grep noise, as I first assumed; the main app target has been
unbuildable in this working tree since 2026-08-24. It also meant I could not verify my (additive)
`NotoVault` change against `Noto` without that temporary move.

**What better looks like:** Delete both files and sweep for other `*sync-conflict*` files across
the repo. Flagged rather than deleted unilaterally — deleting ~9300 lines from Eugene's working
tree is his call, and they are untracked so `git checkout` would not bring them back. Worth a
guard too: a synchronized-group target will compile *anything* dropped into its folder, so an
iCloud conflict inside a source directory is a build break waiting to happen.
