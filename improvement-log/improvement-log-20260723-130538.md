### 2026-07-23 — macOS local build blocked by pbxproj match signing

**What happened:** `flowdeck build -s Noto-macOS` failed with "No profile for team '39GJBP8V5A' matching 'match AppStore com.eugenechan.Noto'". Recovered via the xcconfig override recipe in the `project-macos-local-build-signing` memory (Automatic style + Apple Development identity + ASC API key decoded from `fastlane/.env.default`), costing ~4 minutes and one wasted build.

**Why this matters:** The memory already flags the proper fix as *open*: Debug should be `Automatic` in the pbxproj and the match distribution profile should be applied at gym/export time in the Fastlane lane. Every macOS session pays this tax until that's done. A memory that documents a workaround for a known-fixable defect is a standing cost, not a solution.

**What better looks like:** Fix it once — revert the Debug config to Automatic signing in `Noto.xcodeproj` and move `match AppStore` application into the Fastlane lane, then delete the workaround half of the memory. Until then, the xcconfig + AuthKey setup should be a checked-in script (e.g. `scripts/local-macos-build.sh`) rather than re-assembled by hand each session.

### 2026-07-23 — Full-screen capture leaked an unrelated window's content

**What happened:** To capture a SwiftUI menu popup (which app-scoped ScreenCaptureKit capture excludes), I ran `screencapture -x -R <region>` over the region where Noto's sidebar sits. Noto was not frontmost at that moment, so the capture returned another application's window — private, explicit content unrelated to the task. I deleted the file immediately and switched to activating Noto first.

**Why this was wrong:** A display-region capture captures *whatever is on the display*, not the app. I reasoned about the region in the app's coordinate space and never checked what was actually in front. On a personal machine that's a real privacy failure, not just a bad screenshot.

**What better looks like:** Never use `screencapture -R` without first confirming the target app is frontmost (`System Events` → `frontmost is true`) — or better, prefer app/window-scoped capture (`axdriver screenshot`) and only fall back to region capture for popups, with an explicit frontmost check in the same command chain. Treat any unexpected capture content as a stop-and-delete event.

### 2026-07-23 — Assumed `.frame()` sizes a macOS Menu's hit target

**What happened:** The task was to equalize sidebar header icon sizes and hit targets. The existing code put `.frame(width: 44, height: 44)` on each `Menu`'s label and I assumed that made a 44pt target. It doesn't: macOS menu styling sizes the control from the glyph. The AX frames were 22×14 and 20×14 versus 36×36 for the plain buttons. I tried three variations (frame on the Menu, `Color.clear` in the label, a near-transparent fill) across three build+launch cycles before accepting that SwiftUI `Menu` can't do it and writing an AppKit `NSMenu`-backed button.

**Why this was slow:** I had the measurement tool available from the first minute (`axdriver find` returns exact AX frames) but only used it after the first "fix". Each speculative SwiftUI tweak cost a ~60–90s build plus relaunch; measuring first would have shown immediately that the label frame was being discarded and that the problem was structural, not a modifier ordering issue.

**What better looks like:** For any "make these controls the same size / hit target" task, measure the actual frames of every control *before* editing, and re-measure after each change. When two consecutive style tweaks fail to move a measured number, stop tweaking and change the mechanism.

### 2026-07-23 — Geometry fix that silently disabled the control

**What happened:** `.menuStyle(.button).buttonStyle(.plain)` produced exactly the 36×36 targets I wanted, and I nearly moved on. Pressing the menu did nothing. I only established this was a real regression (rather than an automation limitation) by running a *control test* — pressing an unrelated, unchanged SwiftUI menu elsewhere in the app, which opened fine.

**Why this matters:** I verified the property I was asked about (size) and not the property I was putting at risk (does it still work). The failure was also invisible in a screenshot — the icons looked perfect.

**What better looks like:** When a change alters how a control is *constructed* (style, wrapper, backing view), the verification must exercise the control's behavior, not just its appearance or geometry. And when an automated interaction produces no visible effect, run a control test on an unchanged instance before concluding "the tool can't do this" — that one cheap step converted an assumption into a confirmed bug.

### 2026-07-23 — A `Color` layer inside a Menu label broke window creation

**What happened:** Trying to defeat SwiftUI's image-only-label special case, I wrapped the menu glyph in `ZStack { Color.clear; glyph }` and later `Color.primary.opacity(0.001)`. The app then launched with **zero windows** — process alive, no AX windows, no crash log. I spent several minutes suspecting saved-state restoration and simulator/launch flakiness (clearing `Saved Application State`, launching the binary directly for stderr) before reverting the ZStack, which immediately restored the window.

**Why this was slow:** The symptom (no window at all) looked nothing like the change (a label's background layer), so I defaulted to "environment is flaky" instead of "bisect my own edit". The revert took 90 seconds and was the first thing I should have tried.

**What better looks like:** When an app breaks in a way that seems unrelated to the last edit, revert the last edit *first* — it's the cheapest possible bisect and it either exonerates the change or names the culprit. "That can't be it" is a hypothesis, not evidence. Also worth remembering as a SwiftUI/macOS fact: non-image content inside a `Menu` label can destabilize layout badly enough to prevent window creation.
