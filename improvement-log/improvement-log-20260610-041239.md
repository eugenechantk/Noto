### 2026-06-10 — Recommended an English-only embedding model without checking language needs

**What happened:** In the semantic-search plan, I recommended bge-small-en-v1.5 (English-only) as the embedding model. Eugene's answer to the fork was "is there another multilingual model I can convert from HF to CoreML" — revealing multilingual was a requirement, which cost a second research round.
**Why this was wrong:** Language coverage is a first-order requirement for any embedding/search/NLP model choice, not a footnote. The initial research even flagged "English only" as a con, but I still made it the recommendation instead of surfacing the language question as part of the fork.
**What better looks like:** When recommending models that have language coverage tradeoffs (embeddings, OCR, speech, search), establish the user's language requirements *before* or *within* the recommendation — e.g., make the fork "English-only (smaller/better) vs multilingual (bigger)" explicit, or check what languages the user's actual data contains first.

### 2026-06-10 — Spike declared done without iOS-runtime validation

**What happened:** I reported the Core ML conversion spike complete after validating only via coremltools' Python runtime on macOS. Eugene asked "did you get the model running on a simulator device though?" — the answer was no, and the gap had to be closed afterwards.
**Why this was wrong:** The artifact's entire purpose is to run on iOS. Host-toolchain validation proves conversion correctness but not target-runtime behavior (resource pipeline differences like .mlpackage→.mlmodelc auto-compilation surfaced immediately when I did run it). The project's own ethos — "build and deploy to the simulator, then visually verify" — applies to runtime artifacts, not just UI.
**What better looks like:** A spike validating a deployable artifact (Core ML model, framework, binary resource) is only "done" when it has executed on the target platform runtime — at minimum a simulator test, with physical-device check scheduled if hardware (ANE) matters. Build the runtime check into the spike's exit criteria up front.

### 2026-06-10 — flowdeck simulator create device-type naming quirk

**What happened:** `flowdeck simulator create --device-type "iPad mini (A17 Pro)"` (the display name shown by `flowdeck simulator list`) failed with "Invalid device type" because flowdeck naively maps the name to an identifier keeping the parentheses. The raw identifier form `iPad-mini-A17-Pro` worked.
**Why this matters:** Two failed attempts before the workaround; the same trap will hit any parenthesized device type (most iPads, SE models).
**What better looks like:** When creating simulators for device types with parenthesized names, pass the dash-separated identifier (strip parens) directly, e.g. `iPad-mini-A17-Pro`. Same applies to runtime names — use "iOS 26.2" (exact installed version), not "iOS 26".

### 2026-06-10 — Tool descriptions compete: new agent tools need the OLD tools' descriptions rewritten

**What happened:** After adding the hybrid `search` tool to NotoChat, the flash-lite model kept choosing grep for "what did I talk about my projects in the last 5 days" (~75% of runs) because grep's description still advertised "list the notes matching only the date filters (e.g. notes modified in the last few days)". The independent audit caught it; rewriting grep's description to "EXACT substring matching… prefer `search` for topical questions" + a hard routing rule in the system prompt fixed tool choice to 3/3.
**Why this matters:** Tool selection is a zero-sum choice over the whole toolset. Adding a better tool without re-scoping the descriptions of overlapping older tools leaves cheap models on the old path.
**What better looks like:** When adding an agent tool that overlaps an existing one, always (1) rewrite the old tool's description to its narrowed niche, (2) state the routing rule explicitly in the system prompt with a worked example, (3) verify tool choice empirically across several fresh conversations with the cheapest supported model.

### 2026-06-10 — LocalSecrets.xcconfig side effect: simulators auto-sync real Readwise data

**What happened:** Copying the gitignored `Config/LocalSecrets.xcconfig` into the worktree (needed for the bundled OpenRouter key) also carries `NOTO_READWISE_TOKEN`, so the test simulator's vault auto-synced ~775 real Readwise captures mid-audit, changing the test environment under the auditor (and drowning seeded fixtures in search results).
**Why this matters:** Test environments silently mutating mid-run invalidates seeded-fixture assumptions; the auditor burned time diagnosing it.
**What better looks like:** When enabling secrets in a test build, enumerate every credential in the file and disable unwanted live integrations for tests (blank the Readwise token in the worktree copy, or seed AFTER first sync settles, or assert on differential behavior rather than absolute result sets).

### 2026-06-10 — Diagnosed the wrong Application Support path for the sandboxed macOS app

**What happened:** Investigating "Mac embedding very long", I queried ~/Library/Application Support/Noto/... and concluded the semantic index had never started (empty cache, no semantic.sqlite — my probe even created a misleading 0-byte file). The sandboxed app's real data lives in ~/Library/Containers/com.eugenechan.Noto/Data/Library/Application Support/..., where the index was 85% complete and healthy.
**Why this was wrong:** The project CLAUDE.md explicitly documents that the macOS app is sandboxed; I'd even hit sandbox specifics earlier in the project. One wrong path nearly produced a "it's broken" conclusion for a working system.
**What better looks like:** For the sandboxed macOS Noto app, ALWAYS check ~/Library/Containers/com.eugenechan.Noto/Data/... first for runtime data. Non-container paths only hold data from non-sandboxed debug runs. Also: sqlite3 CLI creates missing files on open — use file existence checks or mode=ro URIs when probing.

### 2026-06-11 — Tunneled on a memory hypothesis while the device was simply out of disk

**What happened:** Debugging the iPad rebuild failure, I built a full memory-tracing experiment (sim + real vault + RSS sampling) around a jetsam hypothesis. The actual trigger was ~53 MB of free storage on the device — revealed incidentally when the install failed, not by my investigation.
**Why this matters:** Device-resource constraints (disk, RAM, thermal) are co-equal first hypotheses for device-specific failures of write-heavy features. Disk was the cheapest to check — one question to Eugene ("how full is your iPad?") or one install attempt — but I tested the expensive hypothesis first. The memory work was still valuable (real secondary risk), but the order was wrong.
**What better looks like:** For "works on device A, fails on device B" with index/cache writes involved: enumerate B's resource ceilings FIRST (storage, RAM class, thermal state) and check the cheap ones before designing experiments. Asking the user for a storage screenshot is a valid diagnostic step.
