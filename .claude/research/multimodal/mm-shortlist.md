# Shortlist

The four reports converge on a clear decision tree, and these four candidates are its pivot points. (1) Unified replacement: the field is fully covered by three failure modes — non-commercial licenses (jina-clip-v2, jina-v5-omni, jina-v4, nomic-embed-multimodal-3b), English-only (Nomic aligned towers), or size (GME, VLM2Vec). Qwen3-VL-Embedding-2B is the single unified model that fails on size/Core ML alone while being Apache and above the granite text bar; verifying its claims (especially 'no sub-1B variant exists' and 'no Core ML path') is what definitively kills or revives the unified architecture. (2) Image-only leg: FG-CLIP2-Base is the only permissive (Apache) EN+ZH dual encoder that fits ~300 MB after embedding-table palettization and beats both SigLIP2-B and Chinese-CLIP on Chinese retrieval while matching SigLIP2-B in English — its license chain, the COCO-CN/Flickr-CNA numbers, the ~285 MB quantization math, and the SigLIP2 Core ML conversion existence proof are the load-bearing claims. If any fail, the decision falls back to SigLIP2-B/mSigLIP (same family, so not separate slots per the no-variants rule). (3) UForm3 multilingual is the only ready-made Apache + EN/ZH + CoreML-in-repo + Swift-SDK option found across all reports (~198 MB pair) — the ship-now hedge whose open question is whether tiny-model retrieval quality clears the bar. (4) SmolVLM2-500M anchors the caption/OCR→granite baseline that report 4 argues captures most retrieval value for a screenshot/receipt-heavy vault at near-zero bundle cost while provably preserving today's EN↔ZH cross-lingual behavior; it is the only budget-and-license-viable vendored captioner before Apple's iOS 27 Foundation Models image input arrives. Excluded from the shortlist despite engineering appeal: Apple MobileCLIP/MobileCLIP2 (apple-amlr research-only license plus English-only CLIP BPE tokenizer — no verification outcome can fix the tokenizer) and all CC-BY-NC/Qwen-Research-licensed models (hard commercial disqualifiers). All four HF IDs were verified live to resolve; live tags already corroborate fg-clip2-base apache-2.0 + en/zh, uform3's in-repo coreml tag, and SmolVLM2's en-only tag.


## Qwen3-VL-Embedding-2B (Qwen/Qwen3-VL-Embedding-2B) — role: unified-replacement
- The HF license is clean Apache-2.0 with no attribution/naming clauses (unlike GME's mandatory 'Built with GME' attribution).
- Total parameter count is ~2.0B, implying ~2 GB at int8 and ~1.1 GB at int4 — i.e. at least 3.5x over the ~300 MB bundle budget even at int4.
- Its text-only multilingual quality is at or above the granite bar: the HF card reports MMTEB mean-task 63.87 / mean-type 55.84 with retrieval-type subscore 78.50, covering 30+ languages including Chinese (noting this task mix differs from the MTEB Multilingual Retrieval set behind granite's 60.3).
- It supports MRL output dims 64–2048 and 32k context, and accepts text, images, screenshots, and video as inputs; the sister 8B is #1 on MMEB-V2 (77.8) and the 2B scores 73.2.
- No Core ML conversion of this or any Qwen-VL-based embedding model exists, and the decoder-VLM dynamic visual token counts make a fixed-shape Core ML/ANE conversion impractical on iPhone-class hardware.
- No sub-1B Apache-licensed variant or distillation of the Qwen3-VL-Embedding family has been released as of June 2026 (this is the claim whose falsification most changes the decision).

## FG-CLIP2-Base (Qihoo 360) (qihoo360/fg-clip2-base) — role: image-leg
- qihoo360/fg-clip2-base is tagged apache-2.0 on HF, its init checkpoint (SigLIP2) is also Apache-2.0, and the bundled Gemma 256k sentencepiece tokenizer file does not carry Gemma model ToU restrictions.
- Total size is 383.8M params (HF safetensors) with a ~197M-param 256k×768 embedding table dominating; int8 weights plus 4-bit palettization of the embedding table yields ~280–285 MB total, and the image tower alone (used per-photo at index time) is ~87 MB int8.
- Chinese retrieval at base size: COCO-CN T→I R@1 62.9 and Flickr-CNA T→I 69.9, beating both SigLIP2-B (46.2 / 49.1) and the Chinese specialist Chinese-CLIP-B (54.9 / 62.4) — per arXiv:2510.10921 Tables 3–4.
- English retrieval at base size meets or beats SigLIP2-B: COCO T→I 54.5 (vs 53.2), Flickr30k T→I 81.9 (vs 78.0), ImageNet-1k zero-shot 79.5 (vs 79.1) — so adopting it over SigLIP2-B costs nothing in English.
- Text tower is 64 max position embeddings (196-token long-caption mode), shared embedding dim 768, fixed 256×256 image input with /255 rescale and mean=std=0.5 normalization — ample for search queries in EN and ZH.
- Core ML conversion is feasible DIY: both towers are vanilla SigLIP2 ViT-B/16 + transformer encoder, and a community SigLIP2-B image-tower Core ML conversion (batmac/ViT-B-16-SigLIP2-Image-CoreML, Apache-2.0) exists as proof; no official Core ML/ONNX artifacts exist for FG-CLIP2 itself.
- The HF implementation is a custom trust_remote_code Fgclip2Model, so tokenizer (sentencepiece, swift-transformers-compatible) and preprocessing must be vendored in Swift — no blocker beyond engineering.

## UForm3 image-text multilingual base (unum-cloud/uform3-image-text-multilingual-base) — role: fallback
- The repo is Apache-2.0 and the model supports 21 languages including Chinese for text→image retrieval.
- Ready-made Core ML artifacts ship in-repo: image_encoder_neural.mlpackage (86.6 MB) + text_encoder_neural.mlpackage (111.2 MB) ≈ ~198 MB pair, plus tokenizer.json — the only off-the-shelf Apache multilingual CoreML image-text pair found.
- A first-party Swift SDK exists (unum-cloud/uform, iOS 16+) that wires the BERT-style multilingual tokenizer via a swift-transformers fork, with measured ANE text encoding of 0.53 ms; the SwiftSemanticSearch demo shows real-time text-to-image search at scale.
- Hard limits: 256-d embeddings, 50-token text limit, 224×224 input.
- Retrieval quality is tiny-model tier — XTD-10 R@10 90.2–96.1 and beats OpenCLIP on COCO-SM non-English, but is well below SigLIP2/FG-CLIP2-class — so it only wins if FG-CLIP2 fails conversion/license verification AND its EN+ZH quality clears a bar on a Noto-like photo eval.
- The uform repo and Swift SDK are still maintained as of June 2026 (the report flagged freshness as unverified).

## SmolVLM2-500M (captioner for caption/OCR→granite baseline) (HuggingFaceTB/SmolVLM2-500M-Video-Instruct) — role: fallback
- License is Apache-2.0 (model card and HF tag), safe for a paid App Store app — unlike Apple FastVLM/MobileCLIP2 which are apple-amlr research-only.
- The 500M model quantizes to ~250–300 MB at int4 (256M variant ~150 MB), fitting the ≤300 MB budget.
- It demonstrably runs on iPhone-class hardware (HF shipped an on-device iPhone demo app on the 500M), making 1–3 s/image one-time captioning realistic — but published phone deployments use MLX/llama.cpp, and a pure Core ML (stateful KV-cache) conversion is an unproven custom project.
- Captions are English-centric — acceptable only because granite's cross-lingual space maps ZH queries onto EN caption text, preserving the EN↔ZH bar (this mechanism is the linchpin of the whole caption architecture).
- Caption-then-text-embed beats phone-scale CLIP embeddings on personal-photo retrieval (CIVIL, arXiv:2510.04010: P@10 0.73 vs 0.58) — but that evidence used 7B-class captioners, so the gap at 500M is unproven and needs a pilot on the actual vault.
- Apple's iOS 27 Foundation Models image input (announced WWDC26, fall 2026, iPhone 15 Pro+) will provide a zero-bundle-MB captioner replacing this model on supported devices — so SmolVLM2 only matters as a stopgap/older-device path.
